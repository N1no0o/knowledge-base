# 架构与设计决策

记录"为什么这么设计"，避免以后自己推翻自己。

## 1. 为什么用 TIL 范式而不是笔记软件

GitHub 已经免费提供了知识库需要的全部底层能力：

| 能力 | GitHub 原生 | 是否需要额外工具 |
|---|---|---|
| 文件组织 | 目录树 | 否 |
| 渲染 | Markdown 自动渲染 | 否 |
| 全文搜索 | 仓库内搜索 | 否（数千篇规模内够用） |
| 版本历史 | 每次 commit 可回溯 | 否 |
| 多端访问 | 网页 / 手机 / 本地 clone | 否 |
| 权限 | 公开 / 私有 | 否 |
| 协作 | PR / Issue / Discussions | 否 |
| AI 接入 | 可被 AI 直接读写 | 否 |

结论：**先不引入任何笔记软件**。哪天真的嫌 GitHub 网页浏览体验差，再加一层发布层（Quartz / MkDocs），但**内容源永远是这个仓库**。

## 2. 为什么"框架与内容分离"

根目录只放框架文件（`AGENTS.md`、`README.md`、`index.md`、`log.md`、`_config.yml`），所有内容进 `notes/<领域>/`。

三个理由：

1. **AI 的检索成本低**：AI 只需要扫 `notes/`，不会被工具脚本和配置干扰
2. **`index.md` 生成逻辑简单**：一个 glob 就能覆盖全部内容
3. **重组安全**：Obsidian 的 wikilink 按**文件名**解析、与路径无关，所以领域目录可以随时重构而不破坏链接

## 3. 为什么下划线开头

`_inbox/`、`_templates/`、`_docs/` 用下划线前缀，是刻意的：

- **Jekyll 默认忽略下划线开头的目录** → 发布到 Pages 时这些内容不会出现在站点上
- 视觉上也能一眼区分"框架"和"内容"

## 4. 为什么 `AGENTS.md` 而不是 `CLAUDE.md`

Claude Code 只自动加载 `CLAUDE.md`，而 Codex / Cursor 等读 `AGENTS.md`。
做法：规则正文只写一份在 `AGENTS.md`，`CLAUDE.md` 里只放一行 `@AGENTS.md` 导入。
这样**规则只有一份，不会漂移**，同时所有 agent 都能读到。

## 5. 四个工作流的设计意图

| 工作流 | 谁主导 | 目的 |
|---|---|---|
| ingest | AI 执行，人决定存什么 | 降低"记下来"的成本 |
| compile | AI 主导 | 把散点变成网络，这是**知识**而非**资料**的分界线 |
| query | 人提问，AI 综合 | 让历史积累产生复利 |
| lint | AI 报告，人决策 | 防腐，防止知识库烂掉 |

核心原则：**编译优先于检索**。不要等提问时才临时检索，要让知识在平时就持续编译成互链结构。

## 6. 已知取舍

- 不做向量检索：数千篇规模内，GitHub 全文搜索 + `index.md` 足够。资料量上万再说
- 不做自动分类：分类由 AI 判断，因为机器分类规则容易把知识切错
- `lint` 只报告不删除：误删笔记的代价远高于留着一篇旧笔记
