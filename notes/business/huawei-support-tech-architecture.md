# 华为云支持服务立项 · 技术方案与架构

**一句话结论：技术论证的目标不是"我们会造轮子"，而是"**能做、成本可控、不重复造轮子**"——所以核心自研只保留三处（统一事件模型 / 聚合与路由引擎 / AI 场景化增强），其余一律主张复用。**

## 一、五层架构

```
数据源层   管理面（平台运维事件│计划内变更│群障/区域故障│服务公告）
          租户面（云监控告警│服务事件(配额/AKSK/资源状态)│客户业务告警）
    ↓ 统一接入（API / 消息 / Webhook / 轮询）
接入与标准化层   事件模型转换│校验去重│时序对齐│租户标识绑定
    ↓
处理与关联层     聚合引擎│关联分析(拓扑/标签/时间窗)│分级引擎│路由引擎
    ↓                        ↓
AI 增强层             触达编排层
 L1 降噪聚合           通道选择/优先级
 L2 摘要生成           送达确认/重试
 L3 影响面分析         配额/熔断
 L4 根因/处置建议      通道: 站内信/IM/邮件/Webhook/APP/短信
    ↓
体验层   订阅管理│通知中心│事件时间线│效果报表│客户平台对接
```

## 二、技术选型（候选，待确认）

| 模块 | 候选 | 备注 |
|---|---|---|
| 消息总线 | 华为云自有消息服务（DMS/MQ） | 优先复用 |
| 流处理 | Flink / 自研 | 聚合引擎核心 |
| 存储 | 时序库 + 对象存储（冷热分层） | ⚠️ 成本关键 |
| AI 推理 | 盘古大模型 / 内部模型服务 | 分级调用降本 |
| 规则引擎 | 自研 or 现有 | 路由/订阅规则 |
| 通道网关 | 统一通道抽象层 | **新增**，避免各通道硬编码 |

## 三、复用 vs 自研（立项必答：别重复造轮子）

| 能力 | 复用 / 自研 |
|---|---|
| 告警采集（云监控）、消息总线（DMS/MQ）、AI 模型（盘古/内部） | ✅ 复用 |
| 通知通道 | 部分复用（增量在**统一编排与路由**） |
| **聚合/路由引擎 · AI 场景化能力 · 统一事件模型** | 🔨 **自研（三处核心增量）** |

**结论话术：**
> "我们不重复建设采集、总线、模型、通道等基础设施，**核心自研投入集中在三处：统一事件模型、聚合与路由引擎、AI 场景化增强** —— 这正是当前华为云缺失、且构成差异化的部分。"

## 四、关键设计要点

**① 统一事件模型**
```
Event { tenant_id, source(管理面/租户面), category(故障/变更/群障/通知),
        severity, resource[], service, region, start_time, status,
        lifecycle: upcoming → open → resolved → closed,
        raw_ref, ai_summary, impact_scope, confidence }
```
⭐ **生命周期状态机**（借鉴 AWS Health）是专业度体现，也让"变更预告"成为自然能力。

**② 聚合策略**：时间窗 + 拓扑关联 + 语义相似度（AI）；⚠️ **必须可展开** —— 聚合后的事件要能下钻看原始事件。

**③ 路由策略**：维度 = 资源标签 / 项目 / 业务线 / 角色 / 客户自定义；支持**分级打扰**与**免打扰时段**；支持**兜底路由**（找不到责任人时路由到服务经理）。

**④ AI 调用分级（降本关键）**
```
L1 降噪 → 小模型/规则（全量）
L2 摘要 → 中模型（聚合后事件，量已降 70%）
L3 影响面 → 大模型（仅 P0/P1）
L4 根因建议 → 大模型（仅 P0，且标注置信度）
```

**⑤ 成本控制设计**：事件限流/降采样（应对告警风暴）、冷热数据分层、AI 分级调用、短信配额与熔断。

## 五、技术难点与风险

| 难点 | 风险 | 对策 | 状态 |
|---|---|---|---|
| 管理面数据获取 | ~~决定性风险~~ | — | ✅ **已打通** |
| **管理面数据质量** | 时延/准确率/覆盖率不达标 | 实测 + 对齐平台侧口径 + 校验机制 | 🔴 **当前重点** |
| 跨服务接口改造 | 依赖多方、进度不可控 | 前期对齐 + 分阶段接入 | 🟡 进行中 |
| AI 准确率 | 误报/漏报影响信任 | 先做 L1/L2，L4 标注置信度 | 🟡 |
| 告警风暴 | 成本与稳定性 | 聚合前置 + 限流 | 🟡 |
| 时延要求 | 30s 内端到端 | 架构上分离快慢路径 | 🟡 |

### ⭐ 管理面数据链路验证（通道已打通，需补实测报告）

| 验证项 | 目标 |
|---|---|
| 事件类型覆盖率 | ≥ 80% |
| 端到端时延（P50/P95） | 平台侧事件产生 → 本产品收到 |
| 数据准确性 | 与平台侧源数据抽样比对，一致性 ≥ 99% |
| 日均事件量级 | 三类数据日均条数（**用于成本测算**） |
| 变更/群障专项 | 变更预告提前量满足 T-7/T-1 |

> **这份验证报告是立项材料里最有分量的一份技术证据** —— 它把"通道打通了"变成可审阅的数字。

## 六、验收指标

事件类型覆盖率 ≥80% ｜ 端到端时延 P0 ≤30s ｜ 通知准确率 ≥95% ｜ 聚合降噪率 ≥70% ｜ 链路可用性 ≥99.9% ｜ 单客户成本 ≤ 预算上限。
