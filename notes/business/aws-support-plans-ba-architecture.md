# AWS 支持计划 BA 业务架构逆向（六视图）

**结论：用华为 4A 的 BA（业务架构）视角对 AWS 支持计划做逆向工程，得到一条可迁移的核心范式 —— 「档位 = 交付主体等级的封装包」，价格差异不是按「服务量」而是按「谁来交付」定价（自助 SS → AI → 池化人力 TP → 具名专人 NR → 指定团队+主动 DT）。AWS 未公开任何业务架构，本设计全部由其对外能力面反推。**

## 一、BA 六视图（核心交付物是「业务能力地图」）

| # | 视图 | 回答的问题 |
|---|---|---|
| 1 | 业务定位（价值链） | 为什么这么分档？ |
| 2 | **业务能力地图（L1/L2/L3）** | 一共有哪些能力、各自什么等级？ |
| 3 | 业务流程 | 能力怎么被执行？ |
| 4 | 业务对象 | 业务在操作什么？ |
| 5 | 业务规则（R1–R10） | 有什么约束与政策？ |
| 6 | 业务角色与组织 | 谁来做？ |

- 7 个 L1 业务域：事件响应 / 主动保障 / 专家咨询 / 工具与 AI / 支持接入 / 商务治理 / 专业服务
- 配套机读件：`ba_capability_matrix.json`（33 项 × 四档 × 交付主体）、`ba_capability_cards.json`
- AA / DA / TA 三个视图**本次未输出**，仅在第 8 章留出映射接口

## 二、⭐ 核心结论：档位 = 交付主体等级的封装包

| 档位 | 解锁的交付主体 | 能力项（AI 及以上） | 价格锚点 | 一句话业务本质 |
|---|:--:|:--:|---|---|
| Basic | `SS` 仅自助 | 1 / 33 | $0 | **产品缺失态**（默认值，非选项） |
| **Business Support+** | + `AI` + `TP` 池化人力 | 18 / 33 | $29/月·账号 | **自助 + 及时人工**：把「能修」变成「有人管」 |
| **Enterprise** | + `NR` 具名专人 | 25 / 33 | $5,000/月·组织 | **有个人为你负责**：把「有人管」变成「有人担责」 |
| **Unified Operations** | + `DT` 团队 + 主动 | 31 / 33 | $50,000/月·组织 | **有一支队替你扛**：把「有人担责」变成「组织级兜底」 |

> **价格差异有据可依**：每一级对应**一种成本结构**（自助→自动化→池化→具名→团队），不是拍脑袋定价。

## 三、价值链：把云上风险转化为可购买的保障

```
①风险识别 → ②保障设计 → ③保障交付 → ④价值实现
 负载定级     能力封装      履约执行     后果兜底
（销售）     （产品定义）  （支持运营） （客户成功）
```
约束规则贯穿：R1/R2 → R5 → R3/R4 → R6/R9。

**两个"非人节点"（关键发现）**：
- 营销段有 AI **替客户**做优先级判断（`Unlimited 24/7 contextual recommendations`，⚠️ 该行 Basic 取值页面自相矛盾）
- 交付段有 AI **替 AWS** 做一线处置（**AWS DevOps Agent**，本账号已实测自动开通与 Agent Space 自建）
⇒ **这是支持体系里第一个进入价值链的「非人交付主体」**。

## 四、可直接复用的 5 条 BA 范式

| # | 范式 | AWS 的做法 | 可迁移性 |
|:--:|---|---|---|
| 1 | 分档轴选「**后果等级**」而非「服务量」 | Default → Production → Business-critical → Mission-critical | ⭐⭐⭐ 后果等级天然锚定客户预算（停机成本） |
| 2 | 用「**交付主体阶梯**」设计价格阶梯 | 自助 → AI → 池化 → 具名 → 团队+主动 | ⭐⭐⭐ 每级对应一种成本结构 |
| 3 | 标准能力**一次性做到底**，溢价只卖稀缺项 | 14 项标准化能力在 BS+ 封顶 | ⭐⭐⭐ 避免「为 1 项能力买整档」的错配抱怨 |
| 4 | 把**权益与激活拆成两个对象** | 矩阵 ✓ ≠ 已开通 | ⭐⭐⭐ 降低「签约即承诺」的交付风险 |
| 5 | AI 作为**交付主体**而非工具 | DevOps Agent 自动创建、自动执行 | ⭐⭐ 需先有自动化资产积累 |

## 五、应识别为业务风险的 3 个结构

| # | 结构 | 风险 |
|:--:|---|---|
| 1 | **降级易、升级需人**（R7） | 客户感知「进容易出难」→ 锁定感；中段黏性最高但也最易招不满 |
| 2 | **响应时间全是「尽力而为」**（R2） | SLA 差异无法在合同层落地 → 客户质疑「多花的钱买到了什么」；须用**资源保障强度**（具名/团队）论证溢价，而非「更快」 |
| 3 | **前置依赖不透明**（R9） | 客户见 `not_available` 会归因于「档位不够」→ **误升级**；应在交付前做前置条件体检 |

## 六、一条跨体系对照（🟡 推演，我方映射需另核）

双方在**顶级故障响应**上都收敛到 **< 5 分钟**，但 BA 视角下含义不同：
AWS 的「5 分钟」绑定在 **IME（事件管理工程师）+ IDR 告警接入**这套机制上 ⇒ 它是**交付主体的函数**，**不接入告警（non-onboarded）承诺即降级**。
⇒ **启示：承诺响应时间时必须同时定义触发条件与技术前置，否则该承诺在交付层无法兑现。**
