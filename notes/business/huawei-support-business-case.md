# 华为云支持服务立项 · 商业计划与成本模型

**一句话结论：收入侧不需要发明新收费机制 —— 只须在既有「云服务收入 × 拆分比例」的三级梯度计费之上，决定哪些能力进哪个梯度、哪些做成梯度内加购；真正的风险全在成本侧，且**所有数值当前均为待填**（⬜）。**

## 一、商业框架前置：钱从哪来

```
收入池 = 云服务收入 × 拆分比例（⬜ 待管理层明确）
        ├── 知识类（边际成本 ≈ 0）→ 底座，不单独定价
        └── 支持类（正边际成本）  → 三级梯度计费，按消费额阶梯费率
```

| 三级序列（纵向·客户规模） | 本产品的商业落点 |
|---|---|
| **尊享级**（年流水 ＞1 亿 · 26 项 · SLA ＜5 分钟） | 全量 AI + 专属规则 + 事件级 API + SLA 时延承诺（与 VIP TAC 配合） |
| **企业级**（21 项 · TAM + AI · SLA ＜10 分钟） | ⭐ **主战场** —— 优护计划在此级内部做标准版/增强版二次分层 |
| **商业级**（14 项 · AI 自助 · SLA ＜10 分钟） | AI 使能自助：基础降噪聚合 + 站内信/邮件（普惠 AI） |
| **底座**：基础知识及基础支持 | 收入池定义来源；本产品通道成本从中回收 |

## 二、⭐ 必须提醒管理层的一处成本事实

**尊享级 SLA ＜5 分钟 vs 企业级 ＜10 分钟，不是"快一倍"，而是交付模式的改变：**

| | 企业级 ＜10 分钟 | 尊享级 ＜5 分钟 |
|---|---|---|
| 值班模式 | 可用共享值班池 | **必须专属值班（含夜间）** |
| 交接成本 | 可跨班次交接 | 交接会吃掉 SLA 预算，**必须无缝** |
| 成本性质 | 变动成本 | **近乎固定成本** |

> **建议：尊享级定价拆成「服务成本 + 风险溢价」两部分**，而不是简单按消费额阶梯加价。
> 本产品（EDR）能**降低**其中一部分成本 —— AI 精准路由减少人工对接与误报打扰，**这是对尊享级经济性的直接贡献**。

## 三、商业模式 = B 路径（能力型 + 分层溢价）

| 层级 | 能力 | 付费 |
|---|---|---|
| **Basic**（随服务） | 站内信 + 邮件 + 基础事件通知 | 免费 |
| **Pro**（增值） | + IM/Webhook/API、精准路由、告警抑制、多通道编排 | 付费 |
| **Enterprise**（增值） | + AI 全套增强、SMS/APP、专属规则、SLA 时延承诺、效果报表 | 付费（溢价最高） |

选 B 路径的 4 条理由：① 贴合"增强公有云用户体验"原始诉求，不被质疑"凭什么收费"；② 基础普惠易推广；③ **AI 增强与高时效通道是真实成本项**，做溢价有合理性；④ 与 AWS Support Plans 分级模式一致，**有行业先例可引用**。

**分层边界原则：**"能力"普惠，"成本/时效/深度"付费 —— 边际成本≈0 的进 Basic；有明显边际成本的（短信、AI 推理、专属人力）进付费层；客户强烈要求集成的（API/Webhook）进 Pro。

### ⚠️⚠️ 重大修正（2026-09-21，已用官网资料核实）

**官方服务目录明确：企业优护计划只在「企业级」支持计划中提供，基础级/开发者级/商业级均不含。**

- ⇒ 原设想的"Basic 层级随服务普惠"在优护框架内**不成立**（优护本身不是普惠产品）
- ⇒ 官方显示 **IM 企业群从商业级起就有**，"多一个 IM 通道"**不能作卖点**

**修正后的分层（推荐方案甲：企业级内分层）：**

| 层级 | 内容 | 原设计对应 |
|---|---|---|
| **优护标准版**（企业级含） | 平台化事件/变更/群障通知 + 精准路由 + 基础降噪聚合 | 替代原 "Basic" |
| **优护增强版**（企业级增值） | + AI 全套增强、API/Webhook、专属规则、SLA 时延承诺、效果报表 | 替代原 "Pro/Enterprise" |
| ~~Basic 普惠~~ | **不存在** —— 优护是企业级专属 | ⚠️ 已废止 |

**两个好处：① 定价难题自动解决**（优护本就是企业级专属，做增值分层不违反"普惠"预期）；**② 销售口径清晰**（不新增支持计划等级，只在该级内部区分标准版/增强版）。**原则不变：存量客户权益只增不减。**

## 四、成本模型

| 成本项 | 计算逻辑 | 备注 |
|---|---|---|
| 事件接入与处理 | 事件量 × 单位计算成本 | 事件量为最大变量 |
| 事件存储 | 事件量 × 保留周期 × 单位存储价 | ⚠️ 保留周期一改成本翻倍 |
| AI 推理 | 调用次数 × 单次 token 成本 | ⚠️ 聚合后再调可大幅降本 |
| **通道成本** | 短信条数 × 单价（**最主要**） | ⚠️ 短信 0.0X 元/条 × 百万条 = 大数 |
| 人力 | 研发 + 运维 + 服务经理 | 分摊 |
| 客户侧配置成本 | 服务经理投入 | 易被忽略 |

**单位经济模型（评审必看这一行）：**
```
单客户月度成本 = 事件处理 + 存储 + AI 推理 + 通道费 + 分摊人力
单客户月度收入 = 支持服务溢价 / 增值包定价
单位毛利 = 收入 − 成本   →  必须为正，且 > X%
```

**⚠️ 成本失控的三个高危点：**
1. **告警风暴** —— 一个故障产生百万级事件 ⇒ 对策：**聚合前置、限流、降采样**
2. **短信通道** —— 客户把它当默认通道 ⇒ 对策：**默认关闭 + 配额 + 熔断**
3. **AI 全量调用** —— 每条事件都调大模型 ⇒ 对策：**只对聚合后事件调 AI，且分级调用**

## 五、收入 / 间接价值 / ROI / GTM

- **收入预测（3 年框架，⬜ 全待填）**：2027 = 试点客户转化 + 头部扩展；2028 = 随支持服务包自然渗透；2029 = 政企/金融铺开。**收入假设必须写明来源**（"试点承诺" vs "行业渗透率推算"）。
- **间接价值（能力型产品最该讲的账）**：咨询工单下降 / 投诉升级下降 / **NPS·续费率提升**（最有说服力）/ 服务经理效率 / 招标加分。
  > ⭐ **杀手锏句**：本产品即使**不直接收费**，只要能让头部客户**续约率提升 1 个百分点**，其价值就远超研发投入。
- **ROI 框架**：3 年总投入 / 直接收入 / 间接收益 / 回本周期 / 3 年 ROI（⬜ 待填）。
- **GTM 五阶段**：试点期（美团/顺丰共建出案例）→ 内嵌期（随支持服务包默认开通基础能力）→ 溢价期（AI 增强包 / Enterprise 增值）→ 规模化（金融/政企/物流打包）→ 生态（上架云市场）。
  获客路径必须落到现有体系：① 现有客户升级 ② 服务经理推荐 ③ 招标技术门槛 ④ 云市场。
